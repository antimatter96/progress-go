# AGENTS.md

Wails v3 desktop app: Go backend (`main.go`, `app.go`) plus a vanilla TypeScript + lit-html frontend bundled by Vite (8.3.8). It tracks study-week progress and persists it as JSON. macOS is the primary target. `wails3` and `github.com/wailsapp/wails/v3` are both 3.1.0, and `go.mod` requires `go 1.26.0`.

## Commands

- Run the app in dev: `wails3 dev` from the repo root (or `mise x -- wails3 dev`). Starts Vite on `http://127.0.0.1:1234` (host and `strictPort` pinned in `frontend/vite.config.mjs`), watches Go files, hot-reloads the frontend, regenerates `frontend/bindings`, and runs the dev bundle `bin/progress.dev.app`. `wails3 dev` reads `build/config.yml`.
- Build the app: `wails3 build` produces the binary `bin/progress`; `wails3 package` builds the `.app` bundle `bin/progress.app`. Launch it with `open bin/progress.app`. The Taskfile runs `npm install`, generated bindings, the frontend build, and icon generation automatically.
- Frontend only: `cd frontend && npm install && npm run dev` (or `npm run build`). In a plain browser the Wails bootstrap is absent and the UI loads hard-coded sample weeks instead of the real file.
- Ignore the README's root-level `npm install`: the root `package-lock.json` is empty. All JS dependencies live in `frontend/`.
- Toolchain is pinned in `mise.toml`: Go 1.26 (matches `go.mod`'s `go 1.26.0`), Node 26, and `wails3` 3.1.0 via the `go:` backend. Run `mise install` and keep them on `PATH`. Without mise, install the CLI with `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.1.0`.
- Check the toolchain before trusting a build: `mise x -- node -v`, `mise x -- go version`, and `mise x -- wails3 version`, while a bare `node -v` here can resolve to a different global Node install than `mise.toml`.

## Gotchas

- `main.go` embeds `frontend/dist`, so `go build`, `go vet`, and `go test` fail with "pattern frontend/dist: no matching files found" until `cd frontend && npm run build` has run once.
- Plain `go build` is not a shippable build even when it succeeds. `wails3 build` compiles with `-tags production`; plain `go build` produces a dev binary that expects `FRONTEND_DEVSERVER_URL`. Treat `wails3 build` (or `wails3 dev`) as the only real build check; the bundle at `bin/progress.app` is the runnable artifact.
- There is no test suite, linter, or typecheck config. `frontend/src/js/tests/week_test.js` is empty, there is no `tsconfig.json`, and Vite (esbuild) strips types without checking them. Do not report a `tsc` or test run as verification; `npm run build` is the real check. After any change to the build pipeline (bundler, Tailwind, CSS tooling), verify dev-mode change pick-up with the checklist in `docs/live-change-tests.md`.
- Deletes are soft: a week stays in the JSON with `deleted: true` and renders as an empty node. Restoring means editing the JSON back to `deleted: false`.
- `frontend/bindings/**` is generated by Wails and tracked in git (see `.gitattributes`) so a frontend-only `npm run build` works without the CLI. Do not hand-edit it; add exported methods on `App` in `app.go` and regenerate with `wails3 dev` or `wails3 generate bindings -ts -i`.
- `build/darwin/Info.plist` and `Info.dev.plist` are generated from `build/config.yml`. Edit the config, then run `wails3 task common:update:build-assets` — never hand-edit the plists. That task also recreates `build/ios`, `build/linux`, and `build/windows`; delete those, this repo ships macOS only.
- Never rerun `wails3 init` in this repo: it re-extracts the scaffold's Wails-logo `Assets.car` and default Taskfiles.
- Icons: `build/appicon.png` generates `build/darwin/icons.icns` via `common:generate:icons`. The liquid-glass `build/appicon.icon/` and the compiled `build/darwin/Assets.car` are committed; regenerate them with `wails3 task common:generate:liquid-glass-icons` only on a Mac with full Xcode 26+ (Icon Composer). Without Xcode, `actool` cannot compile the bundle.
- `ConfirmDelete` uses a v3 callback-based dialog and blocks on a channel until a button is pressed. Binding calls run off the UI thread, so this is safe; do not move dialogs into `ServiceStartup`, where v3 dialogs now no-op.
- `frontend/vite.config.mjs` has three non-obvious settings that must not be removed: `define: { global: 'globalThis' }` (dragula → crossvent → `custom-event` references Node's `global`; without it drag-reorder throws in dev *and* in the packaged app, while `npm run build` still stays green), `server.fs.allow` covering `frontend/` (the `../../bindings` imports sit outside Vite's `root: 'src'`), and `server.host: '127.0.0.1'` (Vite 8 otherwise binds IPv6 `[::1]` while the Wails dev proxy dials IPv4, so every dev page load 502s).

## Architecture

- Go exposes `GetJsonData`, `SaveJsonData`, `SetJsonData`, and `ConfirmDelete` on `App`. The Go side treats the save file as an opaque string; the frontend owns the schema, validation (`Week.Validate`), and migration behavior.
- `main.go` creates the `application.New` options (name, about box, embedded assets, `Mac` options), one `WebviewWindow`, then calls `app.Run()`.
- `frontend/src/js/main.ts` wires the page. `week.ts` is both the `Week` model and its lit-html view. `week_manager.ts` owns the week list, drag ordering, debounced saves, and confetti. `form.ts` is the add-week form. `framework.ts` is the only bridge to Go.
- `framework.ts` is the only bridge to Go and never sniffs for Wails. It calls the bindings and treats a rejected call as "plain browser": `loadLocal()` returns `null` (so `main.ts` loads sample weeks), `saveFile()` ignores the failure, and `customConfirm()` falls back to `window.confirm`. Do not gate on `window._wails` or `_wails.flags`: importing `@wailsio/runtime` creates `_wails` in a plain browser, and Wails v3 injects `_wails.flags` from the `didFinishNavigation` hook, which races `window.onload` (where `run()` starts).
- Saves are debounced: `WeekManager` polls every 5s and writes only when a week changed, and Go also saves in `ServiceShutdown`. Changes that bypass `updateLastChangeTime()` will not re-render or persist.
- The save format is an array of weeks: `videos` (`m`/`s`/`seen`), `solvable` (`activities`, `tutorials`, `assignments`), optional `programmable` (`practice`, `graded`), plus `factor` and time estimates used to project hours. Preserve compatibility with existing files.
- The frontend uses lit-html templates, not LitElement/React: each week is re-rendered wholesale into its container. Event listeners are attached afterwards by DOM id (`${week.id}-...`), so ids and the render order matter.

## Tailwind

- Tailwind is v4 (4.3.5) with CSS-first config: there is no `tailwind.config.js`, and all configuration lives in `frontend/src/style.css` (`@theme`, `@utility`, `@plugin`). It runs through the `@tailwindcss/vite` plugin in `frontend/vite.config.mjs` — there is no `.postcssrc`/`@tailwindcss/postcss` anymore (do not add PostCSS config alongside the plugin; the two would double-process Tailwind).
- The custom `invalid` variant no longer exists: v4 ships `invalid:` built in, so `.basic-input:invalid` styling works without any config.
- Tailwind scans literal class strings in `frontend/**/*.ts` and HTML, scoped by `@import 'tailwindcss' source("../src")` in `style.css` (source detection covers `.ts` lit-html templates — verified under `wails3 dev`). Dynamically assembled class names will not be generated; collections such as `progress`/`progress_bg` in `week.ts` exist for that reason.
- Custom shared classes (`transparent-border`, `good-shadow`, `better-shadow`, `better-button`) are declared as v4 `@utility` in `style.css` so they work both in `@apply` and as regular template classes. Plain `.class` blocks cannot be `@apply`'d in v4.
- v4 shifted utility scales: `shadow-sm` is now v3's `shadow`, so `index.html` uses `shadow-xs` for the old look. Check the v4 upgrade guide before assuming a v3 class name still means the same thing.
- Editing files under `wails3 dev` updates the app window live (verified for plain rules, HTML/TS template utilities, JIT-new classes, `@theme` values, `@utility` bodies, and the nested font import): CSS edits hot-swap instantly, `.ts`/`.html` edits trigger a full page reload (expected — there is no framework HMR plugin). Checks against `localhost:1234` with `curl` reflect the current build (unlike Parcel, Vite's dev server does not serve stale CSS to non-HMR clients).
- `frontend/src/fonts/incolsolata/style.css` is imported from `style.css` with plain quoted syntax (`@import './fonts/incolsolata/style.css' layer(base)`). Using `@import url(...)` for it silently drops every `@font-face` rule from the bundle (Lightning CSS leaves it as a late `@import`, which is then discarded) — fonts vanish with no build error.
