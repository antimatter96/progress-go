# AGENTS.md

Wails v2 desktop app: Go backend (`main.go`, `app.go`) plus a vanilla TypeScript + lit-html frontend bundled by Parcel. It tracks study-week progress and persists it as JSON. macOS is the primary target. Wails CLI and `wails/v2` library are both 2.17.1, and `go.mod` requires `go 1.26.0`.

## Commands

- Run the app in dev: `wails dev` from the repo root. Starts Parcel on `http://localhost:1234`, hot-reloads the frontend, and regenerates `frontend/wailsjs` bindings.
- Build the app: `wails build` from the repo root. Produces the bundle `build/bin/progress.app`; launch it with `open build/bin/progress.app`. Wails runs `frontend:install` / `frontend:build` from `wails.json` automatically before compiling.
- Frontend only: `cd frontend && npm install && npm run dev` (or `npm run build`). In a plain browser, `window.go` is absent and the UI loads hard-coded sample weeks instead of the real file.
- Ignore the README's root-level `npm install`: the root `package-lock.json` is empty. All JS dependencies live in `frontend/`.
- Toolchain is pinned in `mise.toml`: Go 1.26 (matches `go.mod`'s `go 1.26.0`) and Node 26. The `wails` CLI is a mise shim too (2.17.1). Run `mise install` and keep both on `PATH`; don't assume a system-wide Go or Node is the right version.
- Check the toolchain before trusting a build: `mise x -- node -v` / `mise x -- go version` show the pinned versions, while a bare `node -v` here can resolve to a different global Node install than `mise.toml`.

## Gotchas

- `main.go` embeds `frontend/dist`, so `go build`, `go vet`, and `go test` fail with "pattern frontend/dist: no matching files found" until `cd frontend && npm run build` has run once.
- Plain `go build` is not a working build even when it succeeds. Wails only links the desktop frontend under its `production`/`dev` build tags; without them `wails.Run` returns "Wails applications will not build without the correct build tags" (the app prints an `Error:` line and exits without a window). Treat `wails build` (or `wails dev`) as the only real build check; the bundle at `build/bin/progress.app` is the runnable artifact.
- There is no test suite, linter, or typecheck config. `frontend/src/js/tests/week_test.js` is empty, there is no `tsconfig.json`, and Parcel strips types without checking them. Do not report a `tsc` or test run as verification; `npm run build` is the real check.
- Deletes are soft: a week stays in the JSON with `deleted: true` and renders as an empty node. Restoring means editing the JSON back to `deleted: false`.
- `frontend/wailsjs/**` and `build/**` are generated by Wails (see `.gitattributes`). Do not hand-edit the bindings; add exported methods on `App` in `app.go` and regenerate with `wails dev`.

## Architecture

- Go exposes `GetJsonData`, `SaveJsonData`, `SetJsonData`, and `ConfirmDelete` on `App`. The Go side treats the save file as an opaque string; the frontend owns the schema, validation (`Week.Validate`), and migration behavior.
- `frontend/src/js/main.ts` wires the page. `week.ts` is both the `Week` model and its lit-html view. `week_manager.ts` owns the week list, drag ordering, debounced saves, and confetti. `form.ts` is the add-week form. `framework.ts` is the only bridge to Go.
- Saves are debounced: `WeekManager` polls every 5s and writes only when a week changed, and Go also saves on shutdown. Changes that bypass `updateLastChangeTime()` will not re-render or persist.
- The save format is an array of weeks: `videos` (`m`/`s`/`seen`), `solvable` (`activities`, `tutorials`, `assignments`), optional `programmable` (`practice`, `graded`), plus `factor` and time estimates used to project hours. Preserve compatibility with existing files.
- The frontend uses lit-html templates, not LitElement/React: each week is re-rendered wholesale into its container. Event listeners are attached afterwards by DOM id (`${week.id}-...`), so ids and the render order matter.

## Tailwind

- Tailwind is v4 (4.3.5) with CSS-first config: there is no `tailwind.config.js`, and all configuration lives in `frontend/src/style.css` (`@theme`, `@utility`, `@plugin`). PostCSS runs through `@tailwindcss/postcss` (see `frontend/.postcssrc`), not the v3 `tailwindcss` plugin — the v3 plugin name throws under v4.
- The custom `invalid` variant no longer exists: v4 ships `invalid:` built in, so `.basic-input:invalid` styling works without any config.
- Tailwind scans literal class strings in `frontend/**/*.ts` and HTML, scoped by `@import 'tailwindcss' source("../src")` in `style.css` (source detection covers `.ts` lit-html templates — verified under `wails dev`). Dynamically assembled class names will not be generated; collections such as `progress`/`progress_bg` in `week.ts` exist for that reason.
- Custom shared classes (`transparent-border`, `good-shadow`, `better-shadow`, `better-button`) are declared as v4 `@utility` in `style.css` so they work both in `@apply` and as regular template classes. Plain `.class` blocks cannot be `@apply`'d in v4.
- v4 shifted utility scales: `shadow-sm` is now v3's `shadow`, so `index.html` uses `shadow-xs` for the old look. Check the v4 upgrade guide before assuming a v3 class name still means the same thing.
- Editing CSS under `wails dev` updates the browser live (Parcel watch → Tailwind v4 recompile → HMR), verified for plain rules, HTML/TS template utilities, JIT-new classes, `@theme` values, `@utility` bodies, and the nested font import. One quirk: `curl` of the dev server can return a stale cached stylesheet while the browser (on the HMR websocket) gets the fresh one — trust the browser or a Node `fs.readFileSync` check over `curl` when verifying.
- `frontend/src/fonts/incolsolata/style.css` is imported from `style.css` with plain quoted syntax (`@import './fonts/incolsolata/style.css' layer(base)`). Using `@import url(...)` for it silently drops every `@font-face` rule from the bundle (Lightning CSS leaves it as a late `@import`, which is then discarded) — fonts vanish with no build error.
